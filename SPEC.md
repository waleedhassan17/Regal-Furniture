## 1. Background and goal

Regal Furnitures is a Pakistani furniture manufacturer making office, home and school furniture. New orders are currently posted in a factory WhatsApp group. As volume grows, older orders scroll out of sight, some are never started on time, and the team only notices when the client's delivery deadline is close.

The Excel file shows the current practice: one tab per client, one block per furniture item. The delivery date ("DD") and bill number are blank on every tab, and there is nowhere to record status, the person responsible, or payments.

The portal has one job: every order lives in one place and nobody has to remember anything. Opening it should show, within a few seconds, what needs attention today.

**Users.** Around 5 to 15 internal staff. Office staff and the owner use a laptop; factory staff use Android phones, often on a slow connection. They are not technical. English interface.

**What good looks like.** A new person can enter an order without training. Nobody needs to scroll or search to find out what is late. The app looks and feels like a finished product from an established brand, not an admin template.

**Out of scope.** No public website, customer login, online payments, inventory, invoicing or accounting.

## 3. Data model

An order belongs to one client and has many items; in the Excel file an order ranges from 1 item to about 100.

**clients** — name, phone, alternate phone, company (optional), delivery address, city, notes.

**orders** — order number (auto-generated by the database as `RF-YYYY-NNNN`), bill number (optional), client, delivery address (copied from the client, editable per order), order date, delivery deadline (required), production status, delivered at (set by trigger when status becomes Delivered), person responsible, special instructions, created by, archived flag, timestamps.

**order_counters** — one row per year, used by the order-number trigger. Not readable by users.

**order_notes** — order, body, author, created at. An append-only log: anyone active can add a note; each note shows who wrote it and when. *(Decision 2026-10-08: replaces a single "internal notes" field on orders.)*

**order_finance** — one row per order: order amount and delivery charges. This is a separate table on purpose. Row Level Security works on rows, not columns, so keeping money in its own table is what lets the database hide it from factory staff.

**payments** — order, amount, date, method (Cash / Bank transfer / Cheque / Other), note, recorded by.

**order_items** — item name, quantity, size (free text, e.g. `L= 96" W= 42" H= 30"`), sheet/laminate code (e.g. `A.N 4091, 2028`), metal colour, PC, rack, fabric, leather, foam, railing, lock, note, reference image path, item status (Pending / In Production / Ready), sort order. Only name and quantity are required.

**status_history** — order, from status, to status, changed by, changed at. Written by a database trigger so it cannot be skipped.

**profiles** — one per auth user: full name, phone, role (`admin` or `staff`), active flag.

**settings** — single row: due-soon days (default 3), start-warning days (default 10), not-started grace days (default 2).

Seed data (development only) is marked with an `is_seed` flag on clients, orders and profiles so it can be removed without touching real data.

Derived values, never stored: grand total = order amount + delivery charges; received = sum of payments; remaining = grand total − received; days left = delivery deadline − today in the `Asia/Karachi` timezone. Expose days left and attention level through a database view so lists can filter and sort on them, and expose balances through an admin-only view.

Use proper foreign keys, check constraints, enums for statuses, and indexes on the columns used for filtering and sorting. Orders are archived, not hard-deleted.

## 4. Business rules

**Production status:** New (not started) → In Production → Ready for Delivery → Delivered, plus On Hold and Cancelled. Any transition is allowed; each one is recorded in status history.

**Attention level**, for every order that is not Delivered, Cancelled or archived, first match wins:

1. Overdue — the deadline has passed.
2. Due soon — the deadline is within the due-soon days.
3. Needs to start — status is New and either the deadline is within the start-warning days or the order was created more than the grace days ago.
4. On track — everything else.

Keep this logic in one place and cover it, along with the money calculations, with unit tests including boundary dates. *(Implementation: the single source is the SQL function `compute_attention`, used by the `order_overview` view; it is tested from Vitest against the database.)*

**Formats.** Money in PKR as `Rs 125,000`, no decimals. Dates displayed as `08 Oct 2026`. Days left phrased as "5 days left", "Due today", "3 days overdue".

## 5. Roles and security

Email and password login through Supabase Auth. There is no sign-up page; admins create accounts.

- **Admin** — everything. The owner and office staff, who enter orders and handle money, are admins.
- **Staff** — factory staff. View clients, orders and items; change production status and item status; add notes. Cannot see any amounts, cannot read or write `order_finance` or `payments`, cannot create or edit orders or clients, cannot manage users or settings, cannot archive orders.

Requirements:

- RLS enabled on every table, with policies based on the caller's role in `profiles`. A signed-in user with no active profile can read nothing, so a stray self-registration through the API gains nothing.
- The role restrictions are enforced in the database. Hiding a field in the UI is not sufficient. Staff updates to `orders` and `order_items` are limited to the status column by a database trigger.
- Every server action validates its input with Zod and checks the session and role again.
- The service-role key is used only in server-only modules for user management. It must never reach client code.
- Item images go in a private storage bucket and are shown through short-lived signed URLs. Compress images in the browser before upload (longest edge around 1600px) because uploads will come from phones on slow connections.
- Middleware redirects unauthenticated visitors to the login page. Deactivated users are signed out.

## 6. Screens

**Login.** Branded, split layout on desktop with the full logo lockup; clear error messages; forgot-password flow.

**Dashboard.** Count cards for Overdue, Due soon, Needs to start, In production, Ready for delivery, and Delivered this month, each linking to the filtered list. Below, a "Needs attention" list ordered by urgency showing client, item summary, days left, status and person responsible. Admins also see total outstanding balance on open orders. If nothing needs attention, say so plainly.

**Orders list.** Search by client name, phone, order number or bill number. Filters for status, attention level, person responsible and deadline range, kept in the URL so a filtered view can be shared and survives refresh. Default sort is nearest deadline. Server-side pagination. Table on desktop, cards on mobile. Each row shows the days-left badge, the status badge and, for admins, the remaining balance. Status can be changed from the row.

**New / edit order.** One page with sections: client (search existing or create inline, which prefills the address), order details, items, and for admins, amounts. Items can be added, duplicated, reordered and removed; the rarely used fields sit in a collapsible "more details" area; each item accepts a photo, including straight from a phone camera. Live totals. Inline validation. Warn before leaving with unsaved changes.

**Order detail.** Client and address with tap-to-call; deadline and days left; status control; items with photos and per-item status, with progress such as "4 of 7 items ready"; payments with an add-payment dialog and the remaining balance (admin); notes; status timeline. Actions:

- **Print job sheet** — an A4 print layout for the factory floor that follows the Excel block layout (item, qty, size, materials, note, image), carries the logo, order number, client and deadline, and never shows prices.
- **Share on WhatsApp** — opens WhatsApp with a prefilled plain-text summary (order number, client, items, deadline) and a link back to the order. No prices in the message.

**Clients.** Searchable list; a client page with contact details, order history and, for admins, balance.

**Team (admin).** Create users with a temporary password, set role, deactivate and reactivate.

**Settings (admin).** Edit the three reminder thresholds.

## 7. Design direction

Read all eight pages of the brand PDF before designing anything. The interface should feel like the brand: warm, calm, confident, well-made.

- **Colour.** Bone `#F5F1EA` is the page background. Ink `#231F20` is text and the sidebar. Regal Red `#C42126` is for primary actions, key figures and urgent states; Crimson Depth `#8E1620` for hover and pressed. Sand `#E8E0D2` for borders and subtle fills, with white or near-white card surfaces on Bone. Walnut `#5A3A24` as a warm accent. Charcoal `#2A2A2D` for secondary dark surfaces. The guideline is "Bone leads, Ink anchors, Crimson is the moment of conviction": keep red scarce so that it means something, and never put body text on a red background.
- **Type.** Playfair Display for page titles and large dashboard numbers; Montserrat for everything else; both via `next/font`. One line on the PDF's last page mentions "Inter Sans"; ignore it, the typography page and the PDF's embedded fonts are Montserrat. Use tabular figures for money and counts.
- **Logo.** Use the files in `brand/` exactly as supplied: full lockup on the login page, mark only in the collapsed sidebar and as the favicon. Do not redraw, recolour or stretch it. If the logo files are missing, use a plain text wordmark and tell me.
- **Hexagon motif.** The brand frames icons in hexagons. Use this for the dashboard count cards and empty states, sparingly.
- **Status colour.** Brand red for Overdue, a warm amber for Due soon, walnut or sand tones for Needs to start, a muted green for Delivered, neutral for On track. Tune these so they sit comfortably with the brand palette, and always pair colour with a text label.
- **Craft.** Define the palette, type scale, radii and spacing once as design tokens and build every component from them. Soft borders over heavy shadows. Generous spacing. Tap targets at least 44px. Skeleton loading states, helpful empty states, clear error states, toast confirmations for actions. Subtle, quick transitions only.
- **Responsive.** Fully usable at 360px width. Sidebar on desktop, bottom navigation or drawer on mobile.
- **Accessibility.** Text contrast at WCAG AA, visible focus states, labelled form fields, full keyboard operation.

## 8. Engineering standards

- Clear folder structure by feature; no file doing three jobs. Shared UI in one place.
- TypeScript strict, no `any`. Database types kept in sync with the schema.
- Database changes only through numbered SQL files in `supabase/migrations/`. Never edit a migration that has already been applied; add a new one.
- `npm run lint`, `npm run typecheck`, `npm run test` and `npm run build` all pass before a phase is called finished.
- Commit locally at the end of each phase with a descriptive message. Do not push; I handle GitHub. Confirm `.env.local` is ignored by git before the first commit.
- Friendly, human error messages in the UI; details only in server logs.
